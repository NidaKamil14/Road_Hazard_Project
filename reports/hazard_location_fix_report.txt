## 1. Root Cause
In `frontend/app.js` (lines 259–267), whenever the browser's `getCurrentLocation()` failed, timed out, or was denied by the user, the exception was silently caught and assigned a hardcoded fallback to Pune coordinates:
```javascript
let latitude = 18.5204;
let longitude = 73.8567;
try {
  const position = await getCurrentLocation();
  latitude = position.coords.latitude;
  longitude = position.coords.longitude;
} catch (geoErr) {
  console.warn('Geolocation unavailable or denied. Using default location (Pune coordinates).', geoErr);
}
```
Consequences of the bug:
1. Every user reporting a hazard where GPS was slow, unprompted, or disabled unknowingly had their hazard registered at `(18.5204, 73.8567)`.
2. On the authority map, all reported hazards clustered onto that single Pune fallback location.
3. The user had zero feedback or confirmation of what coordinates were being associated with the report.
4. Bounding box coordinates (pixel coordinates in the image) were conceptually disconnected from the geographic report location, but users could not verify the difference.

## 2. Files Modified
1. `frontend/app.js`:
   - Removed the silent Pune fallback `(18.5204, 73.8567)`.
   - Enforced strict browser GPS acquisition via `getCurrentLocation()` with explicit error types (permission denied, position unavailable, timeout).
   - If geolocation is denied or unavailable, the application immediately aborts report submission, creates zero database records, and displays a clear actionable error message.
   - Added user location confirmation: displays `Report location: lat, lng` during analysis.
   - Updated `saveHazardsToDatabase` to attach the exact user GPS coordinates to every detection from that image.
   - Multiple detections from a single image strictly share the same user GPS location while maintaining independent image bounding boxes (`[x1, y1, x2, y2]`).
   - Updated `showResults` and `populateResultsData` to display `Report GPS: lat, lng` alongside image pixel bounding boxes.
2. `frontend/admin.js`:
   - Updated dashboard table to render reported GPS coordinates beneath hazard types.
   - Updated reports table to render reported GPS coordinates in the hazard column.
   - Updated report details view to display formatted GPS coordinates and an interactive `[VIEW ON MAP →]` link.
3. `frontend/map.js`:
   - Added support for `?lat=...&lng=...` URL query parameters, allowing the authority dashboard to open the map focused directly on a specific hazard's GPS location with its popup automatically open.

## 3. Location Flow
The complete geographic location pipeline is strictly:

Browser GPS (`navigator.geolocation.getCurrentPosition`)
  ↓ [Obtains actual user latitude & longitude]
Frontend (`app.js` verifies coordinates and shows confirmation)
  ↓ [Attaches user GPS to each detected hazard]
POST `/hazards` (`{"latitude": user_lat, "longitude": user_lon, ...}`)
  ↓ [FastAPI receives WGS84 decimal degrees]
PostGIS (`POINT(longitude latitude)` with SRID 4326 via `ST_MakePoint`)
  ↓ [Spatial point indexed via GIST in PostgreSQL]
GET `/hazards` or GET `/hazards/{id}` (Returns `{"latitude": user_lat, "longitude": user_lon}`)
  ↓ [Authority Dashboard & Map consume coordinates]
Leaflet Map Marker (`L.marker([latitude, longitude])`)
  ↓ [Marker rendered at exact user GPS location on OpenStreetMap tiles]

## 4. Coordinate Convention
- Browser / API Request Payload:
  - `latitude`: WGS84 decimal degrees (Y axis, -90 to +90)
  - `longitude`: WGS84 decimal degrees (X axis, -180 to +180)
- PostgreSQL / PostGIS Spatial Storage:
  - `POINT(longitude latitude)` with SRID 4326 (where X = longitude, Y = latitude)
  - Column: `location GEOMETRY(Point, 4326)`
- API Response Schema:
  - `latitude`: decimal degrees
  - `longitude`: decimal degrees
- Leaflet Map:
  - `L.marker([latitude, longitude])` (Leaflet standard convention)
